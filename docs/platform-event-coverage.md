# Platform audit and security event coverage

This matrix describes the implemented PostgreSQL audit and security streams after PR #318 and the proposed follow-up in PR #319. It separates the administrative audit trail (`platform_audit_events`) from authentication/session telemetry (`platform_security_events`) and tenant activity (`activity_logs`). “Verified” refers to source/tests named below; it does not certify production grants, backups, retention, or provider configuration.

| Operation | Stream and behavior | Boundary and no-op behavior | Evidence / remaining gap |
| --- | --- | --- | --- |
| Create organization with owner invitation | Platform audit `organization_created`; details contain only whether an invitation was created | Same PostgreSQL transaction as organization/invitation mutation | `backend/services/invitations.py`; organization provisioning coverage in `regression_tests/test_platform_organizations.py` |
| Suspend/reactivate organization | Platform audit `organization_suspended` / `organization_reactivated` | Same transaction; repeated current state is a no-op | `backend/routes/platform_organizations.py`; status transition tests in `regression_tests/test_platform_organizations.py`. Suspension blocks refresh by policy and does not itself clear session `is_active` flags, so it is not recorded as `session_revoked`. |
| Change company role | Platform audit `company_role_changed` only for an actual role transition | Same transaction; unchanged role returns success without a write or audit event | `backend/routes/platform_organizations.py`; PR #319 test `test_unchanged_platform_company_role_does_not_duplicate_audit` |
| Grant/revoke platform administrator | Platform audit `platform_admin_granted` / `platform_admin_revoked` for actual assignment changes | Same transaction; revocation also ends the target’s support sessions. Role loss removes platform authority but does not clear ordinary session activity flags | `backend/routes/platform_organizations.py`; platform-admin lifecycle tests in `regression_tests/test_platform_organizations.py` and support-end tests in `regression_tests/test_platform_support.py`. No session-revoked event is emitted solely for role loss. |
| Save/remove platform announcement | Platform audit `platform_announcement_saved` / `platform_announcement_removed`; safe revision/audience metadata only | Same transaction; removal of an absent announcement has no audit event | `backend/routes/platform_settings.py`; platform announcement tests in the platform settings regression suite |
| Change global security settings | Platform audit `global_security_setting_changed`; records the allowlisted setting key and bounded integer value. If lowering the mobile maximum actually deactivates active mobile sessions, a single aggregate `session_revoked` event records the platform actor, fixed policy reason, mobile flag, and total changed session count | Setting update, expiry changes, and platform audit share a transaction; aggregate security telemetry follows commit. No security event is emitted when no active session is deactivated | `backend/routes/platform_settings.py`; `regression_tests/test_mobile_session_policy.py`. Aggregate event intentionally omits per-account IDs to avoid unbounded fan-out for a platform-wide change. |
| Start/end support session, read through support, denied support access, expiry, logout or implicit support end | Platform audit `support_session_started`, `support_session_ended`, `support_data_read`, `support_access_denied`, or `user_logout`; allowlisted resource/operation/reason and stable IDs only | Support state changes and audit writes share the platform transaction; expiry is recorded when the support service ends an expired row | `backend/routes/platform_support.py`, `backend/services/platform_support.py`; `regression_tests/test_platform_support.py`. Expiry is lazy and is recorded when observed/ended, not by a background sweep. |
| Login, lockout, password reset/change | Global security events `login_succeeded`, `login_failed`, `login_blocked`, reset request/failure/completion, `password_changed`; no raw submitted identifier or reset email in event details | Best-effort after the account mutation transaction; persistence failure does not change auth response and emits a fixed safe diagnostic | `backend/routes/auth.py`; `regression_tests/test_security_account_events.py`, `test_security_reset_events.py`, and `test_security_session_events.py`. This post-commit design has a process-crash gap between mutation and event write. |
| Issue, rotate, replace, expire or revoke browser/native/mobile sessions | Global security `session_issued`, `session_rotated`, `session_revoked`; bounded source/reason/count/mobile fields, never credential values or hashes | Best-effort after commit. Exact refresh retries and no-op revocations do not duplicate events; replacement may have separate revoke/issue writes | `backend/routes/auth.py`; `regression_tests/test_security_session_events.py`, `test_native_bearer_auth.py`. Replacement revoke/issue is not an atomic pair. |
| Remove/deactivate a tenant member | Tenant activity describes the membership mutation; post-commit global `session_revoked` identifies initiating actor, affected account ID, fixed membership reason, and positive count of active sessions actually ended | Membership mutation, support-session end, and session deactivation commit together; security telemetry is written after commit. No active rows, denied/foreign target, or rollback produce no success security event | Proposed `backend/routes/users.py`; PR #319 tests `test_admin_invalidation_records_only_committed_active_sessions` use PostgreSQL and a restricted runtime writer role. Legacy SQLite archive/remove paths do not write to the PostgreSQL global stream. |
| Tenant business changes, inventory/stock changes, restore, ownership/email workflows | Tenant-scoped activity remains the record; these are not copied wholesale into the platform audit/security streams | Existing transaction and tenant authorization rules remain authoritative | Existing route/service activity writers and regression coverage. The matrix does not claim a full inventory of every tenant activity action. |

## Data and access boundaries

- Platform audit and security event writers accept curated action/event enums and safe detail allowlists. The platform audit writer also accepts only `success`, `denied`, or `failure` results.
- Unknown-account login attempts omit the submitted identifier. Reset-failure details contain a fixed reason only. Security events do not include passwords, reset/session/refresh/CSRF tokens, request bodies, or authorization headers.
- `platform_security_events` is outside tenant RLS. Runtime writes require the explicit least-privilege grant helper; development did not apply grants in production. Platform-authorized read API/UI work remains a later task.
- Runtime grant behavior and selected persistence/rollback paths have disposable PostgreSQL regression coverage. A successful CI run is evidence for those tests, not proof of production role grants or provider configuration.
- Operator-supplied audit reasons are bounded free text; the code does not perform generalized PII scrubbing of those strings. Keep reasons concise and free of personal data.
- No retention schedule, purge/archive job, export, backup guarantee, or tamper-evident/immutable storage claim is made. These require separate decisions and operational verification.

## Reviewed but intentionally distinct from session revocation

Organization suspension and platform-admin role removal remain policy/authority changes with their own platform audit records; they do not themselves clear ordinary session active flags. A mobile-duration policy update produces aggregate `session_revoked` telemetry only for active mobile sessions it actually changes to inactive. That event does not identify individual accounts; the audit event records the configuration change.
